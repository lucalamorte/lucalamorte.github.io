PrimeroLab

A study tool for any subject. Notes, PDFs or transcripts are uploaded, flashcards are generated from them, and retention is built with spaced repetition. A study assistant answers questions about the user's own material.

The problem

Generating flashcards from a document used to cut the text at 6,000 characters and drop the rest in silence. For an 80-page PDF, about 95% of the material never reached the model, and nothing on screen said so. The study assistant had a similar blind spot: it ran a keyword search on every message and pushed whatever matched into the prompt, whether or not the question was about the user's material.

Retrieval over the whole document

Making the cut larger would only move the limit. Instead, each document is split into overlapping chunks, every chunk is stored with its embedding in Postgres with pgvector, and only the passages closest to the request are retrieved. The size of a document no longer competes with the context window.

  • Chunks of about 1,200 characters with 150 of overlap, so an idea split at a boundary is not lost.
  • An HNSW index for similarity search, with a documented fallback when the extension version does not support it.
  • The owner's id is repeated on every chunk so the security policy is resolved without a join, which would run per row as the table grows.

An agent instead of guessing

The assistant was turned into a tool-calling agent. The model is given tools and decides which to call: a question about what to review today reads the review queue instead of matching words against flashcards.

Security is structural, not remembered

Every tool queries through the request's own Supabase client, the one carrying the signed-in user's session, so row-level security decides what comes back. The model never supplies a user id and there is no parameter through which it could. A model that asked for someone else's decks would get its own, because that is the only query the database will answer. Tool arguments are clamped on the way in, since they are generated text and not validated input.

Bounded by design

  • 4 tool rounds at most: a loop without a ceiling is a bill without a ceiling.
  • 8 seconds per tool and 6,000 characters per tool result, so one slow or huge answer cannot stall the conversation.
  • The loop mechanics (iteration guard, streamed tool-call fragments, argument clamping) are kept as pure functions so the parts that break silently can be tested.

Two providers, one call

Gemini answers when the deployment is configured for it (through Vertex AI with a service account, or AI Studio with an API key), and OpenAI answers otherwise or when Gemini fails. Every reply records which provider actually answered and why a fallback happened: a silent fallback looks exactly like a provider that was never enabled. Falling back instead of failing is what makes it safe to try a new model on production traffic.

Spaced repetition

Reviews are scheduled with SM-2, kept as pure functions with no database or framework dependency so the rules can be tested directly. SM-2 was chosen over FSRS on purpose: FSRS retains better but needs a model trained on review history that does not exist yet, and the history SM-2 produces is what would make that migration possible later.
