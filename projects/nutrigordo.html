Nutrigordo

A nutrition assistant that lives in Telegram. Meals are logged by text, photo or voice note; calories, macros, training and supplements are tracked; and reports for a nutritionist are generated as PDFs.

The problem

Calorie trackers ask for grams and barcodes. People describe food the way they talk: the usual toast, half an empanada from that place, two of these with a photo, or a two-minute voice note with the whole day. The goal was a tracker that understands that, and still keeps exact numbers that a nutritionist can trust.

The design rule

The model interprets; the code decides. A language model is good at understanding I had the usual, but with two eggs and bad at adding numbers or keeping dates consistent. So the model is only asked for structured fields, and everything that has to be exact is done in code:

  • Totals, averages, report periods and weekly habits are computed in code, never written by the model.
  • Changes that delete or overwrite something go through a second, narrow judgement before they are applied.
  • Every change made by a message can be undone with one tap.
  • No list of foods or keywords exists anywhere: rules are derived from each person's own history and from the order of what they said.

Failures that shaped it

Every real failure was turned into a fixed test, so it cannot come back. A few of them:

A complaint undid a whole voice note

110 calories for one cookie is impossible was read as "undo", and lunch, a snack and an afternoon meal disappeared. An undo request now needs a second judgement; when it fails, the message is read again with undo ruled out, and the complaint corrects that one food.

Midnight broke the calendar

After midnight, "today" and "yesterday" got mixed up and a dessert was filed as an afternoon snack. The day was made to end at 4 AM for logging, replies name the date late at night, and the meal type follows what the person calls it, not the clock.

A walk overwrote the only gym session of the week

A message about walking was taken as a correction of a back workout. Another kind of activity or another routine is now treated as a new session unless the person asks to replace it, so two workouts and a walk can live on the same day.

A product with several sizes got a random one

A can of soda was worth 66 or 106 kcal depending on which size the search found. When a product is sold in several sizes and none was said, the size is asked, with the real sizes as buttons.

The wrong photo was described

Asked about yesterday's dessert, the model looked at the most recent photo (a sandwich) and invented a cookie brand. Earlier photos now reach the model with their time and caption, and it asks for the photo when it does not have it.

Testing and cost

  • Fast tests (no model, no database) run on every push through a git hook and block the deploy if anything fails.
  • Scenario tests replay real conversations against the real model. They cost money, so they are run by family, only for the area that changed.
  • A conversation simulator stresses many flows at once, with a hard cap on paid requests.
  • Products that were not found on the web are remembered for 30 days, so they are not searched and paid for again.

Architecture

  • Channel: Telegram Bot API through a webhook protected by a secret, with inline buttons for every confirmation.
  • Server: a single FastAPI process on Render, deployed on every push to the main branch.
  • Model: OpenAI with structured outputs validated by Pydantic, speech to text for voice notes, and web search for product lookups.
  • Data: Supabase Postgres with row-level security. Each request carries a signed token for that one user, and the service key is never used.
  • Access: closed beta with invitation codes validated on the server; the landing page and its interactive demo are served by the same app.
